# Rolling BIRCH: matched cyclic-GC diagnostic

This is a mechanism follow-up to [calendar v2](../calendar-paired-v2/README.md), not another clustering policy or an addition to the original 42 static/routing runs. [Predeclared setup and reproduction](../../experiments/calendar-gc-diagnostic-v1/README.md), [aggregate measurements](results.json).

## What changed, and what stayed identical

The published v2 implementation/protocol/results remain untouched at base `b2d3db7`. The only intervention is a full `gc.collect()` immediately after replacing the old model at each 2,048-arrival rebuild. Both arms have identical weakref/lifecycle instrumentation; automatic Python GC remains enabled. Four fresh processes ran in order automatic 1, explicit 1, explicit 2, automatic 2, then an unchanged v2 control.

After loss of temporary files, the official hash-verified UCI source and pinned E5 safetensors/tokenizer were reconstructed with the original CPU dependency lock. Sampling and all 13,824 vectors were regenerated by the unchanged v1/v2 preparation scripts. Every current prediction matched across both arms, both repeats and the uninstrumented control. All 28 daily counts, CF counts, scores and rebuild counts matched published v2 exactly. Original private vector/prediction bytes are unavailable, so byte identity to the previous session is not asserted. The same 5 rebuild arrivals were 2,048 / 4,096 / 6,144 / 8,192 / 10,240.

All numbers below are fresh-process measurements on this one pilot. MiB = 2²⁰ bytes. Peak increments use each worker's post-pre-touch, matched-import/API-warmup baseline, not another worker's baseline.

|---|---:|---:|---:|---:|---:|
| Automatic GC | 181.43 / 184.87 MiB | 68.22 / 70.00 MiB | 67.82 / 68.61 MiB | none | 12.67 / 13.33 s |
| Explicit GC after swap | 178.24 / 183.63 MiB | 30.59 / 31.42 MiB | 30.20 / 29.91 MiB | 194.98 / 177.25 ms | 12.22 / 12.78 s |

Explicit collection pauses were 29.71–45.01 ms apiece. The apparent total-time difference is not a speed claim: two repetitions with instrumentation are insufficient for throughput or tail-latency conclusions.

### Object lifetime and lifecycle points

Retired cohorts contained 60 / 58 / 67 / 61 / 66 linked leaf nodes (including dummy heads). In both automatic repeats, all 312 observed retired nodes were still alive at the fifth post-swap observation. In both explicit repeats, every cohort was alive immediately after its own swap and all observed retired nodes were gone after collection. sklearn 1.8.0's linked leaves hold `prev_leaf_` and `next_leaf_` references; weakref observations support delayed reclamation of these cyclic structures in this run. The collected-object count includes more than observed leaves and is not a byte count.

For the last rebuild, anonymous RSS at **before / overlap / after swap / after GC or no-op**, in MiB:

| Arm/repeat | Before | Old/new overlap | After swap | After collection/no-op |
|---|---:|---:|---:|---:|
| Automatic 1 | 140.36 | 142.51 | 142.51 | 142.51 |
| Automatic 2 | 138.32 | 143.32 | 143.32 | 143.32 |
| Explicit 1 | 108.84 | 108.86 | 108.86 | 108.86 |
| Explicit 2 | 108.55 | 108.57 | 108.57 | 108.57 |

Thus removing observed unreachable leaves does **not** immediately return their RSS to the OS. Lower accumulation on later rebuilds is consistent with reuse of reclaimed memory. This does not isolate allocator retention from all other resident memory, nor prove complete native-array reclamation: weakrefs observe leaf objects, not every allocation. Both delayed cyclic collection and retained/reusable process memory may matter. Do not describe this as a leak fix or an exact ownership decomposition.

## Boundaries and next step

The nominal 5 ms sampler can miss short transients or be delayed by the GIL/scheduler; synchronous lifecycle probes supplement it. Old/new trees still overlap, and an explicit-GC version is **not** a hard memory cap. Baseline/RSS components differ across processes; compare within-run increments and report both repetitions. No direct absolute-memory comparison to an earlier session is intended. The diagnostic itself adds weakrefs/probes to both arms.

Estimator serialization is unchanged and excludes the replay/controller: rolling's numeric replay payload is separately 3 MiB plus Python overhead, already included in RSS, not a complete saved restart image. No private/raw input, vector or individual prediction is exported here.

Before changing rebuild triggers or capacity policies, include this explicit-collection arm as a lifecycle control. Its 30–45 ms full-GC pause needs a workload/latency budget and broader validation before production use. This pilot does not establish an aggregate maintenance-policy ranking across tasks or any recommendation-business improvement.
